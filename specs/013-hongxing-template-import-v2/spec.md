# Feature Specification: 荭杏研发绩效模板导入与流程适配 v2

**Feature Branch**: `013-hongxing-template-import-v2`

**Created**: 2026-10-14

**Status**: Implementing — import policy convergence

**Input**: `docs/hongxing-workbook-codex-handoff.md` 与 `/Users/simon/Downloads/荭杏研发项目绩效考核表 (1).xlsx`

## Scope and source precedence

本 Feature 以新 Excel 二进制文件为业务事实源，Markdown 交接文档作为解析索引、背景说明和审计摘要。源文件 SHA-256 为 `50bcf21db2fb357a5a471ecef459353b974355c2b7191e3f920fa708c3735fb3`。任何导入、诊断或回归报告都必须保存文件哈希、工作表名和来源单元格，避免以旧 catalog 或手工猜测覆盖新事实。

源文件包含 21 个工作表：1 个流程说明表、18 个岗位月度模板、2 个 HR 汇总表；岗位模板共 137 个指标，源部门 9 个。系统可以另外维护“机器人事业研发部”作为组织父部门，但不把它伪装成源表部门。`05-算法开发-工程师` 的部门单元格为空时，按同岗位组映射到“算法开发部”，同时保留原始空值和映射原因。

岗位模板中的评分人列和权重是最终计算事实；流程表只作为流程顺序和默认会签说明。PM、部门负责人、CTO、产品经理是业务职责类型，不等于 RBAC 角色，也不因账号后来被改成普通员工而失去已经创建考核中的职责快照。

推荐的会签默认值为：研发部门负责人由本人确认并由 CTO 会签；普通研发工程师由本人、PM、产品经理会签；产品部门负责人和工程师由本人、CTO 会签。流程表中“CTO 只需要签字”作为说明保留，工程师不额外强制 CTO，除非 HR 在模板会签配置中显式勾选。模板显式配置优先于默认值。

## User Scenarios & Testing

### User Story 1 - 校验并导入新版 Excel 模板 (Priority: P1)

HR 或系统维护人员可以上传/指定一份新版工作簿进行只读校验，看到部门、岗位、指标、评分职责、公式和异常，再决定是否导入。校验失败时不生成半套模板。

**Why this priority**: 新规则必须先可追溯、可诊断，才能避免当前评分流程、PDF 和汇总出现数据不一致。

**Independent Test**: 使用给定 SHA 的工作簿运行校验，得到 21 张表、18 套岗位模板、137 个指标、9 个源部门，并列出维度内权重异常、shared formula 和 HR 汇总公式断档；使用损坏或缺少部门映射的副本时导入被阻止且无业务数据变更。

**Acceptance Scenarios**:

1. **Given** 给定 SHA 的原始工作簿，**When** 执行只读校验，**Then** 报告工作簿哈希、所有工作表、岗位/部门/指标计数及每个指标的来源行。
2. **Given** 工作簿包含 Excel shared formula，**When** 解析任意子单元格，**Then** 得到展开后的公式和同等计算结果，不把空 `<f>` 节点当作无公式。
3. **Given** 任一岗位模板存在维度内权重合计异常，**When** 请求发布，**Then** 保留原值并显示来源告警；若逐项舍入的综合权重合计为 100 且无其他阻断则允许发布，否则原子拒绝。
4. **Given** 导入事务中任一岗位或部门失败，**When** 事务结束，**Then** 新增目录、模板、指标和导入记录全部回滚。

### User Story 2 - 以模板事实维护和发布岗位规则 (Priority: P1)

HR 可以查看导入的岗位模板，维护维度、指标、评分标准、数据来源、必填状态、评分职责和会签职责；修正异常后发布新版本。已发布版本不可破坏性覆盖。

**Why this priority**: HR 需要持续维护模板，而历史考核必须继续使用创建时的规则。

**Independent Test**: 原表全部 18 套模板综合权重合计均为 100，维度内合计异常仅告警并允许发布；综合权重不为 100 的修订副本拒绝发布。维护新版本时已发布版本和既有考核不变。

**Acceptance Scenarios**:

1. **Given** 模板维度和指标均来自工作簿，**When** HR 查看模板，**Then** 展示维度占比、维度内权重、综合权重、评分人职责、评分标准、数据来源和来源单元格。
2. **Given** 一套模板逐项舍入后的综合权重合计为 100，**When** HR 发布，**Then** 发布成功并生成不可变版本。
3. **Given** 维度内权重合计超过或低于 100，**When** HR 尝试发布，**Then** 展示维度与来源行告警，不单独作为发布阻断；综合权重合计必须为 100，系统不静默归一化原值。
4. **Given** 模板已被考核使用，**When** HR 编辑或停用后续版本，**Then** 历史模板版本及历史考核仍可读取和导出。
5. **Given** 同一部门、岗位和周期已经有一个当前发布版本，**When** HR 发布新来源版本，**Then** 新版本成为唯一 active 版本，旧版本原子变为 retired 并保留为历史；手动发布草稿与新来源“导入并发布”遵循相同规则。

### User Story 3 - 按岗位自动匹配评分职责并创建考核 (Priority: P1)

创建考核时，系统根据被考核人的部门、岗位类型和周期匹配唯一已发布模板，解析 PM、部门负责人、CTO、产品经理等职责对应的实际员工，并生成评分任务和职责快照。

**Why this priority**: 评分人必须随模板和组织关系解析，不能因固定 RBAC 角色、下拉列表分页或岗位名称猜测而遗漏 CTO、普通员工或子部门负责人。

**Independent Test**: 为负责人、工程师和产品岗位各创建一份考核，确认模板、指标数量、每项评分职责和实际用户正确；缺少任一职责账号时创建被拒绝并给出具体缺失职责。

**Acceptance Scenarios**:

1. **Given** 员工部门、岗位和周期存在唯一已发布模板，**When** 创建考核，**Then** 自动绑定该模板并生成完整指标、评分人和会签快照。
2. **Given** 评分职责对应员工只是普通员工 RBAC 角色，**When** 创建考核，**Then** 仍按业务职责解析该员工，RBAC 角色不作为评分人筛选条件。
3. **Given** CTO、部门负责人、PM 或产品经理职责无法解析，**When** 创建考核，**Then** 返回缺失职责和候选范围，禁止创建半成品考核。
4. **Given** 组织或角色后来发生变化，**When** 查看已创建考核，**Then** 原评分人、职责、权重和会签规则仍保持创建时快照。

### User Story 4 - 按必填指标评分、计算总分并进入确认 (Priority: P1)

评分人按照模板负责的指标填写 0–100 分和意见。系统区分未评分、有效 0 分和不适用，只有所有必填指标完成有效评分后才能进入员工确认；总分和等级按模板公式计算。

**Why this priority**: 这是避免空白被当作 0 分、评分顺序错乱和总分不一致的核心业务门禁。

**Independent Test**: 使用工作簿权重填写一组完整分数，验证每项综合权重、加权得分、总分和等级；只漏一项必填指标时确认请求被拒绝，填写 0 分时可以继续。

**Acceptance Scenarios**:

1. **Given** 维度占比和维度内权重已知，**When** 计算指标，**Then** 综合权重为 `ROUND(维度占比 × 维度内权重 / 100, 1)`，加权得分为 `ROUND(综合权重 × 得分 / 100, 2)`。
2. **Given** 所有必填指标均有 0–100 数值评分，**When** 汇总，**Then** 总分为加权得分之和，等级按 S≥90、A≥80、B≥70、C≥60、D<60 映射。
3. **Given** 一个必填指标为空或仅有未提交草稿，**When** 请求员工确认，**Then** 返回未完成指标清单，状态不变。
4. **Given** 一个指标明确允许不适用且有理由，**When** 提交不适用，**Then** 按模板规则记录并从门禁中正确处理；未显式允许的不适用仍视为未完成。
5. **Given** 同一指标有多个有效评分，**When** 计算，**Then** 取有效评分算术平均并保留每位评分人的原始分数和意见。
6. **Given** Excel 流程表要求员工先提交工作总结与后续计划，**When** 员工未提交总结就尝试自评，**Then** 后端拒绝自评并返回 `WORK_SUMMARY_REQUIRED`。
7. **Given** PM 尚未提交其评分任务，**When** 第二或第三顺位评分人尝试提交，**Then** 后端返回 `SCORING_SEQUENCE_BLOCKED`，前序任务状态不变。

### User Story 5 - 诊断 HR 月度/季度汇总并冻结历史结果 (Priority: P2)

HR 可以查看月度、季度和年度汇总的来源、公式和诊断状态；汇总同时保存数值总分、等级、投入占比、加权贡献和计算版本。已完成考核的结果、导出字段和快照不因模板更新改变。

**Why this priority**: 新模板若不能解释汇总公式和历史结果，线上年度统计仍会出现不可追溯的不一致。

**Independent Test**: 运行两张 HR 汇总表的公式诊断，定位季度表序号 13 行 I/J 公式断档；用两个投入占比样例验证阈值，修改模板后重复导出旧考核并比较结果完全一致。

**Acceptance Scenarios**:

1. **Given** HR 汇总表存在 shared formula 或缺失公式，**When** 诊断，**Then** 报告工作表、单元格、预期公式及阻断级别，不静默填入业务数据。
2. **Given** 项目投入占比低于 20%，**When** 计算汇总，**Then** 加权贡献为 0；达到或超过 20% 时按总分乘有效投入占比计算。
3. **Given** 模板已发布且考核已创建，**When** HR 修改模板，**Then** 旧考核的结果、等级、导出字段、模板哈希和计算版本保持不变。
4. **Given** 汇总或导出失败，**When** 用户查看页面，**Then** 显示可理解错误、请求标识和重试入口，不返回部分汇总结果。
5. **Given** 同一员工同一周期有多个项目考核及投入占比，**When** HR 查看汇总，**Then** 按项目分别展示分数、占比和加权贡献，年度汇总只聚合已完成周期并按有效投入占比计算。

### Edge Cases

- 第一张流程表排在岗位模板之前；解析不能把流程表当作岗位模板。
- 部门、岗位或评分职责为空、重名或有多个候选时必须阻止发布/创建并列出冲突。
- `05-算法开发-工程师` 部门原始值为空，必须使用受控映射并保留 raw 值。
- 维度内权重为 73%、120% 或 140% 等异常时保留源值；只有综合权重逐项舍入后合计 100 才能发布。
- Excel 公式使用 shared formula、数组公式或公式断档时，必须区分“可展开”“需人工修复”和“空白行”。
- 文本评分标准只有阈值或扣分描述时不自动猜测算法，评分人手工提交 0–100 分。
- 已停用模板不得创建新考核，但历史考核仍可查看、确认、补充签字材料和导出。
- 评分人账号停用、转岗或 RBAC 角色变化不改写已创建任务；新考核必须重新解析并校验。
- 导入失败、发布失败、确认门禁失败或汇总诊断失败不得产生半成品数据。
- HR 表仅有序号的空白模板行不算真实数据行，缺公式保留 warning；B:H 任一真实输入（包括 0 分和 0 占比）即算数据行，即使没有序号，缺公式仍 blocking。
- 修订 Excel 后须按实际上传内容重新解析并生成新 SHA 版本；同 SHA 重新校验刷新当前诊断，不重写已导入模板或历史快照。保存草稿不得隐式发布，复用已发布模板不得伪称其已变为草稿。
- 模板列表默认只展示草稿和当前发布版本；retired 版本必须显式打开“显示历史版本”后查看，且被历史考核引用的版本不得物理删除。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 将指定 Excel 文件作为导入事实源，并保存 SHA-256、版本、工作表名称和来源单元格；Markdown 只能作为解析索引，不得覆盖 Excel 数值。
- **FR-002**: 系统 MUST 识别流程表、18 套岗位模板和 2 张 HR 汇总表，不得按固定工作表下标假定岗位模板位置。
- **FR-003**: 系统 MUST 导入 9 个源部门、岗位层级、18 套月度模板和 137 个指标；缺失部门必须通过显式映射处理并保留 raw 值。
- **FR-004**: 系统 MUST 展开 Excel shared formula，保留原公式、展开公式、来源单元格和诊断状态；不得把 `formula=null` 的 shared 子节点误判为无公式。
- **FR-005**: 系统 MUST 使用 Excel 模板实际的维度、指标、评分人和权重；流程表规则只能作为默认说明或冲突诊断来源。
- **FR-006**: 系统 MUST 按 `ROUND(维度占比 × 维度内权重 / 100, 1)` 和 `ROUND(综合权重 × 得分 / 100, 2)` 计算，使用十进制定点半入上舍，禁止使用未声明的归一化。
- **FR-007**: 系统 MUST 区分未评分、有效 0 分和不适用；未显式允许不适用的必填指标必须有 0–100 数值评分才能通过确认门禁。
- **FR-008**: 系统 MUST 阻止综合权重逐项舍入后不等于 100 的模板发布，并显示维度、指标、来源行和修复建议；允许草稿保存原始异常。
- **FR-009**: 系统 MUST 将 PM、部门负责人、CTO、产品经理保存为业务评分职责类型，不得用系统角色名称替代；每个指标的评分职责必须可追溯。
- **FR-010**: 系统 MUST 按部门、岗位类型和周期自动匹配唯一已发布模板；不能因分页、姓名排序或 RBAC 角色过滤遗漏候选人。
- **FR-011**: 系统 MUST 在创建考核时解析实际评分员工、会签员工和评分顺序；任何必需职责无法解析时必须原子拒绝创建。
- **FR-012**: 系统 MUST 保存模板、指标、权重、职责、会签、导出布局、来源哈希和计算版本的考核快照；模板和组织变更不得改写历史快照。
- **FR-013**: 系统 MUST 在所有必填评分完成前阻止进入员工确认，并返回未完成指标和责任人；评分提交、平均值和计算结果必须可审计。
- **FR-014**: 系统 MUST 计算总分、等级、投入占比和加权贡献，并保存月度、季度、年度的数值、等级及计算版本；低于 20% 的投入占比贡献为 0。
- **FR-015**: 系统 MUST 对 HR 汇总公式、shared formula、公式断档和无法解释的文本规则生成诊断，不得静默猜测或填充业务分数。
- **FR-016**: 系统 MUST 提供模板导入预览、诊断、发布、版本查询和失败重试的稳定接口；写操作必须返回成功/失败状态、错误码和请求标识。
- **FR-017**: 系统 MUST 对导入、模板发布、评分提交、总分计算、确认门禁、汇总和导出记录审计信息，敏感字段不得进入响应。
- **FR-018**: 系统 MUST 保留旧模板、旧考核、旧导出和补充签字材料兼容路径；新规则不得通过清库或重建数据卷上线。
- **FR-019**: 系统 MUST 允许 HR 在发布前修正导入模板，发布后通过新版本维护；不得破坏性覆盖被历史考核引用的版本。
- **FR-020**: 系统 MUST 为零指标、空岗位、停用评分人、重复模板、导入中途失败、公式断档和部分汇总失败提供可操作页面反馈。
- **FR-021**: 系统 MUST 流程表要求的员工工作总结、问题风险、所需支持和后续计划作为新流程自评前置门禁，并保存提交时间与审计事件。
- **FR-022**: 系统 MUST 将 PM、第二顺位（部门负责人/CTO）、第三顺位（产品经理）写入评分任务并在后端强制提交顺序，不能只依赖页面显示顺序。
- **FR-023**: 系统 MUST 保存每条考核的项目名称和投入占比，并在月度、季度、年度汇总中聚合多项目贡献；低于 20% 的项目贡献为 0，年度不把空周期计入分母。
- **FR-024**: 系统 MUST 保留孤立评分任务的人工预览和显式清理路径，清理只能删除确认过的 orphan ID 并写审计；当前发布模板不得直接删除。

### Key Entities

- **SourceWorkbook**：原始工作簿的哈希、版本、来源路径、导入时间和解析器版本。
- **SourceSheet**：工作表名称、类别（流程/岗位/HR 汇总）、顺序、来源范围和诊断状态。
- **PositionTemplate**：部门、岗位类型、周期、版本、状态、源工作表和发布信息。
- **Dimension**：模板维度名称、维度占比、排序、原始值与校验状态。
- **Indicator**：指标名称、维度内权重、综合权重、评分标准、数据来源、必填和不适用策略、来源单元格。
- **ScorerRule**：业务职责类型、权重/指标绑定、解析策略和解析到的员工快照。
- **SignoffRule**：本人、PM、部门负责人、CTO、产品经理等会签职责及是否必签。
- **ImportDiagnostic**：错误/警告级别、代码、工作表、单元格、原始值、解析值和修复建议。
- **HRAggregationRule**：月度、季度、年度汇总字段、公式、阈值、来源单元格和诊断状态。
- **EvaluationSnapshot**：考核创建时完整规则、人员、导出布局、哈希和计算版本的只读副本。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 给定 SHA 的工作簿解析结果稳定识别 21 张表、18 套岗位模板、137 个指标和 9 个源部门，重复运行结果差异为 0。
- **SC-002**: shared formula 子单元格和主单元格的展开结果 100% 通过公式结构和样例值对照，公式断档均被诊断而不是静默跳过。
- **SC-003**: 仅维度内合计异常且综合权重为 100% 的模板不被误阻断；综合权重不为 100% 的模板 100% 拒绝发布。原表 18 套模板均可通过权重门禁，来源告警完整保留。
- **SC-004**: 负责人、普通工程师、产品岗位的考核创建均能 100% 生成正确模板、评分职责、会签和历史快照；职责缺失时 100% 拒绝半成品创建。
- **SC-005**: 任一必填指标未完成时确认请求 100% 被阻止；有效 0 分不被误判为空白或 D 等级。
- **SC-006**: 同一输入权重和分数下，系统总分、等级、月度/季度/年度汇总与 Excel 可解释规则的对照结果达到 100% 一致。
- **SC-007**: 模板发布后修改不会改变历史考核的指标、权重、评分人、总分、等级、导出字段或签字材料，重复导出结果校验码保持一致。
- **SC-008**: 导入、发布、评分、确认、汇总和导出失败均展示明确错误、请求标识和重试入口，不出现静默失败或部分成功。

## Assumptions

- Excel 文件由 HR 提供并在导入前保持不可变；新的业务规则通过新的源文件版本进入系统。
- Excel 模板评分人列优先于流程表的概括性文字；流程表和模板冲突时生成诊断并采用模板事实。
- 评分标准中的自然语言阈值第一阶段只展示给评分人，不自动推导实际分数；自动评分需另立 Feature。
- 按 2026-10-01 已确认 A 方案，保留原权重且不归一化；维度内合计异常只告警，综合权重逐项舍入后合计为 100 才能保存、发布和计算；异常草稿允许保留以便 HR 维护。
- 评分职责解析依赖现有组织关系和授权数据；系统不为满足模板而凭空创建员工账号。
- 新功能与旧考核通过兼容模型并存，迁移只允许确定性、可审计的记录，禁止直接清空生产数据库。
- Docker 构建、启动和正式环境回归由用户执行；实现阶段只提供可重复的验证命令和页面验收步骤。
