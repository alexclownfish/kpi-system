# Feature Specification: MVP 验收与回归基线

**Feature Branch**: `001-mvp-acceptance-baseline`

**Created**: 2026-09-17

**Status**: Draft

**Input**: User description: "为现有 KPI MVP 建立可重复、可定位失败且不污染持久化数据的验收与回归基线。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 验证员工创建与初始登录 (Priority: P1)

HR 管理员希望用同一套可重复的验收流程创建普通员工和部门负责人，并确认新员工能够使用
初始密码登录，从而避免密码丢失、角色错配或页面静默失败再次出现。

**Why this priority**: 员工账号是所有考核流程的入口；账号无法创建或无法登录会阻断整个 MVP。

**Independent Test**: 使用 HR 测试身份分别创建一个普通员工和一个部门负责人，验证成功反馈、
角色、数据范围和初始密码登录，最后清理临时员工。

**Acceptance Scenarios**:

1. **Given** HR 已登录且选择有效部门和直属上级，**When** 创建普通员工，**Then** 系统明确提示
   创建成功，新员工可以使用初始密码登录，并获得普通员工权限和本人数据范围。
2. **Given** HR 已登录且选择部门负责人角色，**When** 创建无直属上级的部门负责人，**Then**
   系统创建成功，新员工可以登录，并获得部门负责人权限和部门数据范围。
3. **Given** 创建请求缺少初始密码、普通员工直属上级或使用重复邮箱，**When** HR 提交，**Then**
   系统拒绝请求并展示可理解、可操作的错误，且不产生不完整员工记录。

---

### User Story 2 - 验证权限与数据隔离 (Priority: P1)

系统负责人希望重复验证不同角色只能访问获授权功能和数据，确保菜单变化、接口调整或查询优化
不会造成越权访问。

**Why this priority**: 权限和数据隔离是本项目的核心安全边界，任何回归都可能泄露全公司绩效数据。

**Independent Test**: 使用 HR、部门负责人和普通员工三类身份执行允许与拒绝场景，检查功能权限、
数据范围和直接访问受保护资源的结果。

**Acceptance Scenarios**:

1. **Given** 普通员工已登录，**When** 请求员工管理或公司级统计能力，**Then** 系统拒绝访问，
   且不会返回受保护数据。
2. **Given** 普通员工已登录，**When** 查询员工或考核数据，**Then** 结果只包含本人允许的数据。
3. **Given** 部门负责人已登录，**When** 查询员工或考核数据，**Then** 结果限定在其部门范围内。
4. **Given** HR 已登录，**When** 执行员工管理能力，**Then** 允许操作，但不能通过业务角色能力
   修改或删除超级管理员。

---

### User Story 3 - 一键确认部署可用 (Priority: P2)

开发者或部署人员希望在本地或验收环境用一套简短流程确认系统已启动、统一入口可访问、前后端
能够通信，并获得清晰的失败位置。

**Why this priority**: 构建成功并不代表运行可用；统一的运行验收能减少环境和代理配置问题。

**Independent Test**: 在保留已有数据的前提下启动系统，检查服务状态、健康接口、登录页面和登录
接口，并输出每一步的通过或失败结果。

**Acceptance Scenarios**:

1. **Given** 运行环境满足项目要求，**When** 执行验收入口，**Then** 系统确认后端、前端和统一
   网关均可用，并明确报告每项结果。
2. **Given** 任一服务未启动或接口异常，**When** 执行验收入口，**Then** 流程以失败状态结束，
   指出失败场景，不将部分成功误报为整体成功。
3. **Given** 环境中已有业务数据，**When** 重建、重启并执行验收，**Then** 原有数据和持久化卷
   保持不变。

---

### User Story 4 - 快速定位回归原因 (Priority: P3)

维护者希望验收失败时能直接知道失败的用户故事、角色、请求阶段和预期结果，而不是只能翻阅大量
服务日志。

**Why this priority**: 明确的失败信息可以缩短缺陷定位时间，并让非原作者也能维护验收流程。

**Independent Test**: 人为提供错误凭据或使一个依赖不可用，确认验收结果指出具体失败场景，
并保留足够上下文用于诊断，但不泄露密码、令牌或密码哈希。

**Acceptance Scenarios**:

1. **Given** 某个验收场景失败，**When** 查看结果，**Then** 可以识别对应用户故事、执行步骤、
   预期结果和实际结果。
2. **Given** 验收涉及登录和临时账号，**When** 输出结果，**Then** 不显示明文密码、完整令牌或
   密码哈希。

### Edge Cases

- 验收开始前已存在同名或同邮箱临时员工时，必须使用新的唯一标识，不得覆盖既有数据。
- 创建第一个临时员工成功、后续步骤失败时，仍必须清理已创建的临时记录。
- 清理失败时，结果必须明确列出遗留记录的唯一标识和 ID，禁止静默忽略。
- 普通员工的直属上级已停用或不在指定部门时，创建必须失败并说明原因。
- 健康接口成功但登录页面或认证接口失败时，整体部署验收必须失败。
- 权限拒绝场景必须区分“正确拒绝”和“服务异常”，不得将任意非成功响应都视为通过。
- 验收过程中不得执行删除持久化卷、重置数据库或修改种子账号的操作。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供一个可重复执行的 MVP 验收入口，并按用户故事报告结果。
- **FR-002**: 验收 MUST 覆盖 HR 创建普通员工及其使用初始密码登录的完整流程。
- **FR-003**: 验收 MUST 覆盖 HR 创建部门负责人及其使用初始密码登录的完整流程。
- **FR-004**: 创建员工场景 MUST 验证角色、数据范围、初始密码和用户可见反馈。
- **FR-005**: 验收 MUST 覆盖至少一个缺少必填字段、一个重复邮箱和一个权限不足的拒绝场景。
- **FR-006**: 权限验收 MUST 同时包含允许场景和拒绝场景，并确认拒绝响应不包含受保护数据。
- **FR-007**: 数据隔离验收 MUST 覆盖普通员工本人范围和部门负责人部门范围。
- **FR-008**: 部署验收 MUST 检查后端健康状态、前端登录页面、统一入口和认证链路。
- **FR-009**: 任一必需场景失败时，验收 MUST 返回整体失败，并指出具体失败场景。
- **FR-010**: 临时测试数据 MUST 使用唯一标识创建，并在成功或失败后按精确 ID 清理。
- **FR-011**: 验收 MUST 保留现有数据库、种子账号和持久化数据卷，不得依赖清空环境才能通过。
- **FR-012**: 验收输出 MUST 隐去明文密码、完整认证令牌、密码哈希和其他认证秘密。
- **FR-013**: 清理失败 MUST 作为显式失败报告，并包含可供人工处理的记录 ID 和非敏感标识。
- **FR-014**: 项目 MUST 提供一份与验收入口一致的人工快速验证说明。

### Key Entities

- **Acceptance Scenario**：一个独立可判定通过或失败的用户流程，包含角色、前置条件、操作、
  预期结果和清理规则。
- **Test Identity**：验收使用的种子身份或临时身份；记录角色和用途，但不保存或输出认证秘密。
- **Temporary Record**：验收过程中创建的员工等业务记录，必须有唯一标识、精确 ID 和清理状态。
- **Acceptance Result**：一次验收的汇总，包含各场景状态、失败阶段、非敏感实际结果和整体结论。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 所有 P1 验收场景可在一次执行中完成，并在 5 分钟内给出明确结果。
- **SC-002**: 连续执行验收 3 次，均不因上一次运行遗留的临时数据而失败。
- **SC-003**: 每次成功执行后临时业务记录遗留数量为 0；清理失败时报告率为 100%。
- **SC-004**: 权限验收至少覆盖 3 类角色、2 个允许场景和 2 个拒绝场景。
- **SC-005**: 验收失败时，维护者无需查看源码即可从结果中识别失败用户故事和执行阶段。
- **SC-006**: 验收前后的既有种子账号数量、角色、密码和持久化卷保持不变。
- **SC-007**: 人工快速验证说明可由未参与实现的开发者在 10 分钟内完成。

## Assumptions

- 使用现有 JWT 邮箱密码认证和现有种子账号，不在本 Feature 中引入新的认证方式。
- 验收针对本地或隔离的测试环境，不针对生产环境直接创建测试员工。
- 当前正式业务代码位于仓库根目录；`kpi-main/` 不在本 Feature 的修改范围。
- `DEPARTMENT_TREE` 的真实递归能力不在本 Feature 范围，本次只验证已明确支持的数据范围。
- 本 Feature 建立验收和回归能力，不重新设计七角色 Permission 模型。
