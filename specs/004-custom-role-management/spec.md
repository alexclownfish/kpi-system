# Feature Specification: 用户角色与权限管理

**Feature Branch**: `main`

**Created**: 2026-09-17

**Status**: Proposed MVP

**Input**: 在“组织与绩效”中新增“用户角色”，允许授权管理员创建自定义角色、配置功能权限与数据范围，并将角色分配给用户。

## Clarifications

### Session 2026-09-17

- Q: 一个用户在 MVP 中可以拥有几个业务角色？ → A: 一个用户一个主角色；权限通过该角色继承，不提供用户级额外权限。
- Q: 系统内置角色是否允许直接修改？ → A: 系统角色只读并可复制，自定义角色可编辑和删除。
- Q: 自定义角色如何确定可见数据？ → A: 每个角色必须选择且只能选择一个数据范围。

## User Scenarios & Testing

### User Story 1 - 创建自定义角色 (Priority: P1)

具备角色创建权限的管理员进入“组织与绩效 / 用户角色”，填写角色名称和说明，选择一个数据范围并勾选功能权限，创建可分配的新角色。

**Why this priority**: 这是摆脱代码写死角色、支持企业按职责配置权限的核心价值。

**Independent Test**: 创建“绩效复核员”，赋予考核查看、审核和部门数据范围；创建后角色出现在列表和员工角色选择器中。

**Acceptance Scenarios**:

1. **Given** 管理员具备角色创建权限，**When** 提交唯一名称、数据范围和合法权限集合，**Then** 系统创建自定义角色并明确提示成功。
2. **Given** 用户不具备角色创建权限，**When** 直接调用创建接口，**Then** 系统拒绝且不写入任何角色数据。
3. **Given** 管理员选择了自己不具备的权限或更宽的数据范围，**When** 提交角色，**Then** 系统拒绝越权授权。

---

### User Story 2 - 管理角色权限 (Priority: P1)

授权管理员可以查看角色详情，按业务模块配置权限，修改自定义角色的名称、说明、数据范围、直属上级要求和权限集合。

**Why this priority**: 自定义角色必须可维护，才能适应职责变化。

**Independent Test**: 修改一个未分配给当前操作者的自定义角色权限，重新登录该角色用户后，菜单和后端接口访问能力同步变化。

**Acceptance Scenarios**:

1. **Given** 自定义角色存在，**When** 管理员保存新的权限集合，**Then** 权限替换必须原子完成并记录审计日志。
2. **Given** 目标是系统角色，**When** 管理员尝试编辑或删除，**Then** 系统拒绝并提示可复制为自定义角色。
3. **Given** 自定义角色仍绑定用户，**When** 管理员尝试删除，**Then** 系统拒绝并显示绑定人数。

---

### User Story 3 - 为用户分配角色 (Priority: P1)

具备员工角色分配权限的管理员可以从角色页面或员工页面将一个可分配角色绑定给一个或多个用户。

**Why this priority**: 创建角色后必须能安全应用到实际用户。

**Independent Test**: 将自定义角色分配给测试用户后，该用户重新获取身份信息即可得到新角色名称、权限和数据范围。

**Acceptance Scenarios**:

1. **Given** 管理员有分配权限且目标角色可分配，**When** 为用户更换角色，**Then** 用户原角色被新角色原子替换。
2. **Given** 操作会移除最后一个超级管理员，**When** 提交更换，**Then** 系统拒绝以避免系统失去管理员。
3. **Given** 操作者无权授予目标角色中的全部权限或数据范围，**When** 尝试分配，**Then** 系统拒绝权限提升。

---

### User Story 4 - 查看角色与用户关系 (Priority: P2)

角色页面展示系统/自定义类型、数据范围、权限数量、绑定用户数量和用户明细，方便管理员审计。

**Why this priority**: 管理员需要在修改或删除前确认影响范围。

**Independent Test**: 角色列表统计与用户角色绑定数据一致，超出操作者员工数据范围的用户详情不会泄露。

### Edge Cases

- 角色名称去除首尾空格后不能为空，且大小写不敏感地唯一；角色代码由系统生成且不可修改。
- 至少保留一个有效超级管理员；超级管理员系统角色不能删除、编辑或被复制覆盖。
- 自定义角色有绑定用户时不能删除，需先完成用户改派。
- 权限变更后已有登录会话在下一次身份刷新时生效；后端每次请求仍从数据库校验权限，不依赖前端缓存。
- 删除、更新权限和批量分配发生错误时必须整体回滚。
- `DEPARTMENT_TREE` 在部门层级尚未实现前不得在自定义角色页面伪装为完整可用范围。
- 用户直属上级是组织关系，不自动由权限推断；角色通过“必须指定直属上级”属性表达创建/编辑时的校验要求。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 在“组织与绩效”下提供“用户角色”入口，并仅向具备 `role:view` 权限的用户显示。
- **FR-002**: 角色列表 MUST 展示名称、类型、数据范围、权限数量、绑定用户数量和可执行操作。
- **FR-003**: 具备 `role:create` 权限的用户 MUST 能创建名称唯一的自定义角色，并配置说明、单一数据范围、直属上级要求和权限集合。
- **FR-004**: 自定义角色代码 MUST 由系统生成、全局唯一且创建后不可修改。
- **FR-005**: 权限选择 MUST 按业务模块分组，并显示权限名称和说明，不要求管理员手工输入权限代码。
- **FR-006**: 系统 MUST 自动满足基础权限依赖；选择创建、编辑、删除或审批类权限时必须同时包含对应查看权限。
- **FR-007**: 操作者 MUST NOT 创建、编辑或分配包含其自身不具备权限或更宽数据范围的角色。
- **FR-008**: 每个用户在 MVP 中 MUST 只有一个主角色；角色更换必须原子替换旧绑定。
- **FR-009**: 系统角色 MUST 为只读，不允许编辑或删除；管理员可以将系统角色复制为新的自定义角色。
- **FR-010**: 自定义角色有绑定用户时 MUST 禁止删除；无绑定用户时具备 `role:delete` 权限的用户可以删除。
- **FR-011**: 系统 MUST 保证至少存在一个有效超级管理员，不允许删除或改派最后一个超级管理员。
- **FR-012**: 角色创建、权限更新、复制、删除和用户角色分配 MUST 写入审计日志。
- **FR-013**: 后端 MUST 以角色权限和数据范围作为授权依据，前端菜单和按钮只作为同步展示，不能作为安全边界。
- **FR-014**: 自定义角色 MUST 能在现有员工创建、编辑和独立角色分配入口中使用。
- **FR-015**: 系统 MUST 消除业务流程对固定 `hr/manager/employee` 角色代码的依赖；功能行为由权限、数据范围和组织关系决定。
- **FR-016**: 用户角色页面的所有写操作 MUST 显示提交中、成功和可操作的失败反馈。
- **FR-017**: 用户角色详情 MUST 提供绑定用户列表，但用户明细必须受操作者员工数据范围限制。
- **FR-018**: MVP MUST NOT 提供用户级直接权限、一个用户多角色、字段级权限、条件表达式权限或部门层级继承。

### Key Entities

- **角色**: 一组权限、一个数据范围和组织校验属性的命名集合；区分受保护系统角色与可维护自定义角色。
- **权限**: 稳定的资源与操作能力目录，例如查看员工、创建考核、导出报表。
- **数据范围**: 决定用户可访问哪些员工、考核和报表数据的单一范围。
- **用户角色绑定**: 用户与其唯一主角色的关联，角色更换时原子替换。
- **角色审计事件**: 记录创建、修改、复制、删除和分配操作的操作者、对象、结果和变更摘要。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 授权管理员可在 3 分钟内创建并分配一个自定义角色。
- **SC-002**: 角色权限或数据范围变更后，用户刷新身份信息即可获得一致的新菜单和接口访问结果。
- **SC-003**: 越权授权、编辑系统角色、删除已使用角色和移除最后超级管理员的自动测试全部被拒绝且不产生部分写入。
- **SC-004**: 所有角色写操作均有审计记录，角色列表的用户计数与实际绑定一致。
- **SC-005**: 自定义角色用户不依赖固定角色代码即可完成其被授予的业务操作。

## Assumptions

- MVP 采用一个用户一个主角色，后续如需多角色可在现有关系表上演进。
- 初始只有超级管理员拥有角色创建、编辑和删除权限；HR 可继续分配其有权授予的非保护角色。
- 系统权限目录仍由版本化代码维护，管理员只组合已有权限，不在页面创建新的权限代码。
- `SELF`、`DIRECT_SUBORDINATES`、`DEPARTMENT`、`ASSIGNED`、`ALL` 可供选择；`DEPARTMENT_TREE` 暂不开放。
