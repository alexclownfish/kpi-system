# Feature Specification: 可维护部门层级与负责人

**Created**: 2026-10-01
**Status**: Ready for planning
**Input**: 部门层级需要自己设置；子部门负责人不能指定父部门负责人，上级候选为空。

## User Scenarios & Testing

### User Story 1 - 自主管理部门组织关系 (Priority: P1)
管理员在部门管理设置上级部门和本部门负责人，不再依靠猜测角色或重复配置评分职责。
**Why this priority**: 组织关系必须能由实际业务维护。
**Independent Test**: 编辑任意部门，保存上级和负责人，刷新后持久；根部门可无上级。
**Acceptance Scenarios**:
1. 部门列表明确展示上级部门和负责人；编辑可选择上级及本部门在职员工为负责人，允许清空。
2. 自身/子孙部门不能成为上级；跨部门、停用、不可见员工不能被设置为负责人。
3. 重启不覆盖维护结果；没有权限不能修改，保存有提交、成功和失败反馈。

### User Story 2 - 父部门负责人可成为直属上级和评分人 (Priority: P1)
配置父部门负责人后，子部门负责人能选择该人作为直属上级，并在新的考核使用同一上级。
**Why this priority**: 修复截图中空列表，保证组织配置和评分一致。
**Independent Test**: 无DEPARTMENT_MANAGER评分职责时，已配置父部门负责人仍可选，并作为新考核的上级评分人。
**Acceptance Scenarios**:
1. 明确配置部门负责人后，不需要重复添加部门评分职责；负责人身份不依赖权限角色、岗位文本或内置部门名称。
2. 合法直属上级优先；否则最近上级部门明确负责人优先；该层未指定时兼容既有有效部门评分职责，最后公司CTO。
3. 工程师由本部门明确负责人评分；自评分、循环上级、停用或离开该部门的失效负责人拒绝，不静默兜底。
4. 多个旧职责候选仍要求明确选择，历史考核快照和任务不变。

### Edge Cases
- 新建部门尚无所属员工，先建部门再设置负责人；不虚构员工或自动授予角色。
- 已设置负责人停用/调岗后显示失效并阻止错误评分，不清空历史数据。
- 手工调整层级后保留已有直属上级字段；不再合法时明确提示重新选择，不批量改历史。
- 无负责人设置的部门仍兼容原职责规则；不将任一“部门负责人角色”员工自动认定为负责人。

## Requirements
### Functional Requirements
- **FR-001**: 管理员能维护任意部门上级/负责人及清空，列表可见，刷新/重启保留。
- **FR-002**: 部门负责人只能是本部门在职且在管理员数据范围内的员工，不改角色、账号或历史数据。
- **FR-003**: 部门层级拒绝自身/子孙循环，上级候选排除无效父关系，保留既有后端循环保护。
- **FR-004**: 子部门负责人上级候选、员工保存和评分解析均认可显式父部门负责人，不强制重复维护评分职责；身份支持自定义部门和岗位。
- **FR-005**: 合法直属上级优先，祖先逐层明确负责人优先于该层旧职责，最后CTO；工程师本部门明确负责人优先；无明确负责人时兼容旧规则。
- **FR-006**: 拒绝失效负责人、自评、循环和超范围访问；不基于权限角色猜测负责人。
- **FR-007**: 提供自动化和隔离页面证据；用户自行重建普通Compose，不清库、不切换环境、不修改部署开关。

### Key Entities
- 部门：上级部门、明确负责人、所属员工。
- 直属上级：员工明确选择的合法组织上级。
- 部门评分人：来自明确部门负责人，未配置时兼容既有职责。

## Success Criteria
### Measurable Outcomes
- **SC-001**: 任意部门维护和刷新验收通过，重启覆盖次数为零。
- **SC-002**: 无重复职责配置下，父负责人可选并评分，候选/保存/预览评分人差异为零。
- **SC-003**: 停用、调岗、自己、循环、权限拒绝场景全部通过，历史变更次数为零。

## Assumptions
- 每个部门最多一位明确负责人，管理员指定；不猜测现有账号。
- 部门负责人配置不授予任何访问权限；评分访问沿用已有任务与权限控制。
- 009的初始层级只作首次默认值，后续维护优先；不扩大其它评分职责或流程开关的范围。
- 无需要阻塞的问题；人员选择由部门管理页面完成。
