# Feature Specification: 评分职责候选员工完整加载

**Feature Branch**: 不创建新分支，沿用当前工作区
**Created**: 2026-10-02
**Status**: Ready for planning
**Input**: CTO、普通员工与子部门负责人未出现在评分职责的评分人下拉列表。

## User Scenarios & Testing

### User Story 1 - 选择完整的评分人名单 (Priority: P1)

维护人员新增或编辑评分职责时，可以选择权限范围内所有启用员工，不因员工排序或人数被遗漏。

**Why this priority**: 员工遗漏直接阻止正确的评分职责配置。
**Independent Test**: 使用 17 人及 205 人名单，选择第 10 名之后的 CTO、子部门负责人和普通员工。
**Acceptance Scenarios**:

1. Given 有 17 名可见启用员工，When 打开新增评分职责，Then 全部 17 名可选，包含 CTO、子部门负责人和普通员工。
2. Given 有 205 名可见启用员工，When 打开评分人选择，Then 全部 205 名可选且无重复。
3. Given 员工被停用或不在操作者数据范围内，When 加载名单，Then 该员工不出现在候选名单。

### User Story 2 - 加载不完整时阻止误配置 (Priority: P2)

加载中或任意一页加载失败时，维护人员不能使用旧名单或残缺名单保存职责；失败后可以刷新重试。

**Why this priority**: 防止看似成功的半份名单误导配置。
**Independent Test**: 模拟第二页失败，确认提示失败且新增、编辑、评分人选择及保存不可用，重试成功后恢复。
**Acceptance Scenarios**:

1. Given 数据正在加载，When 尝试新增或保存，Then 操作不可用。
2. Given 后续页读取失败，When 加载结束，Then 显示失败而不是暂无配置，不保留旧候选名单，可刷新重试。
3. Given 无可见启用员工，When 打开新增职责，Then 显示无可选启用员工并禁用评分人选择和保存。

### Edge Cases

- 零人、恰好 100 人、101 人和超过 200 人。
- 第二页失败必须整体失败，不返回第一页作为完整名单。
- 并发人员新增、删除、停用不承诺跨页事务快照；后端保存仍校验人员状态。

## Requirements

### Functional Requirements

- **FR-001**: 完整加载当前权限范围内的启用员工，不以角色名称过滤候选人。
- **FR-002**: 员工数超过单页容量仍全部可选；稳定名单中不遗漏、不重复。
- **FR-003**: 保留已有访问权限和数据范围，不扩大可见员工范围或授予员工任何新权限。
- **FR-004**: 所有候选数据加载成功前禁用新增、编辑、评分人选择和保存；加载失败清空旧数据并给出重试入口。
- **FR-005**: 空名单提示无可选启用员工，不允许保存。
- **FR-006**: 不改写现有评分职责、已创建考核或评分任务；不改变工作流启用模式。

### Key Entities

- 员工：既有人员身份、姓名、邮箱、启用状态及所属组织，角色不决定能否列入候选。
- 候选名单：操作者可见的启用员工集合，不新增持久化数据。
- 加载状态：加载中、全部就绪、失败；只有全部就绪才允许配置。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 17 人和 205 人固定名单均 100% 可选，含第 10 名后的三类员工。
- **SC-002**: 所有失败与加载中场景均不能使用残缺名单保存，刷新后可恢复。
- **SC-003**: 停用和范围外员工候选数为零，既有职责和考核不发生变更。

## Assumptions

- 复用既有员工访问权限；员工查看范围不足是权限配置问题，不以本次修复绕过。
- 本次不涉及初始化账号、业务职责调整、工作流启用或正式 Docker 服务重建。
- 缺陷修复必须包含自动化回归及隔离环境的真实页面操作验证。
