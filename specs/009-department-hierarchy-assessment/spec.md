# Feature Specification: 部门层级与考核创建一致性

**Created**: 2026-10-01
**Status**: Ready for planning
**Input**: 修复创建考核失败和白屏；运控、结构、嵌入式、软件应用开发归属机器人事业研发部，子部门负责人由机器人事业研发部负责人或 CTO 考核。

## User Scenarios & Testing

### User Story 1 - 创建失败可诊断且不白屏 (Priority: P1)
**Why this priority**: 创建为考核入口，错误必须可处理。
**Independent Test**: 模板不匹配、缺少评分职责和创建开关关闭时，页面保留且显示具体原因；条件齐备时创建成功。
**Acceptance Scenarios**:
1. 模板与员工岗位不同，预览显示员工实际岗位及缺失原因，不遗留其他员工模板。
2. 模板已匹配但评分职责未配置，仍显示匹配模板，列出具体缺失职责；预览和创建使用同一规则。
3. 创建返回结构化错误或旧字符串错误时，显示文本，不崩溃；提交中禁止重复提交。

### User Story 2 - 真实部门父子关系 (Priority: P1)
**Why this priority**: 组织关系决定上级考核和可见范围。
**Independent Test**: 新库及旧库补齐四子部门层级；可编辑父部门，不能成环或删除有子部门的父部门。
**Acceptance Scenarios**:
1. 运控部、结构部门、嵌入式开发部、软件应用开发部属于机器人事业研发部，其余原表部门不猜测归属。
2. 初始化和更新保留员工、模板、既有考核和 HR 后续组织修改。
3. 部门管理展示上级部门并可维护；无关部门的人员不能作为子部门负责人直属上级。

### User Story 3 - 子部门负责人由上级考核 (Priority: P1)
**Why this priority**: 必须避免负责人给自己评分。
**Independent Test**: 工程师由本部门负责人评分；部门负责人由显式直属上级、上级部门负责人或 CTO 评分，评分任务及预览一致。
**Acceptance Scenarios**:
1. 负责人直属上级可选上级部门负责人或明确 CTO 职责账号，与权限角色是否为普通员工无关。
2. 模板中部门负责人职责用于考核部门负责人时，优先其合法直属上级；未指定时使用最近上级部门负责人职责，再无则使用公司 CTO 职责。
3. 自评、无关部门、停用账号不能被用作负责人评分人；多个同级候选不随机选人；缺失仍报具体错误。
4. 父部门的 DEPARTMENT_TREE 范围可查看子树，DEPARTMENT 范围仍只本部门，ASSIGNED 保留评分任务访问。

### Edge Cases
- 缺少真实 CTO/上级负责人账号，不造人，不自动授予权限；明确告知配置缺失。
- 重名初始部门或已有不一致父关系不猜测覆盖，初始化拒绝并回滚。
- 仅兼容原表部门名称前缀加“工程师/负责人/部门负责人”的明确岗位写法；其它岗位不宽泛套用模板，不改员工原值。
- 历史考核快照和已生成任务保持不变。

## Requirements
### Functional Requirements
- **FR-001**: 创建页必须解析两种错误结构为文本，显示详细原因，不白屏，防重复提交。
- **FR-002**: 预览和实际创建必须按同一流程模式、模板匹配及评分职责规则运行；模板匹配成功但职责失败须保留模板及缺失说明。
- **FR-003**: 部门支持父关系和层级维护，校验存在性、自引用、循环及有子部门删除保护。
- **FR-004**: 新旧数据库都幂等补齐指定四子部门的父部门；保留 HR 后续修改和历史人员考核，无新增演示账号。
- **FR-005**: 子部门负责人允许合法跨部门直属上级，候选和后端校验一致；自引用和循环直属关系拒绝。
- **FR-006**: 部门负责人评分规则按 US3 优先级解析，排除被考核者，不从 RBAC 或无关部门猜人。
- **FR-007**: 真正实现部门子树数据范围，保持其它范围和授权边界；预览亦需员工范围校验。
- **FR-008**: 提供测试证据和 localhost 验收方法，不代用户重建日常 Compose、不清库、不改历史快照。
- **FR-009**: 原表部门的“部门名＋工程师/负责人”岗位等价匹配原表标准岗位，预览、创建、直属上级及评分职责匹配一致；非目录部门和不明确职位仍拒绝。

### Key Entities
- 部门：可选上级部门，不能循环。
- 员工：部门、岗位、直属上级；岗位与权限角色分离。
- 评分职责：真实负责人/CTO/项目和产品评分职责，含作用域和有效期。
- 考核预览：匹配模板、评分人和阻塞原因。

## Success Criteria
- **SC-001**: 四指定子部门均正确挂接，重复初始化新增重复及 HR 修改覆盖为零。
- **SC-002**: 两种错误响应和缺少配置场景页面崩溃次数为零。
- **SC-003**: 工程师与负责人解析覆盖允许、拒绝和缺失场景，预览和创建评分人差异为零，无自评分任务。
- **SC-004**: 父子树可见性及无关部门拒绝场景通过，历史考核内容改变次数为零。

## Assumptions
- 只为用户明确点名的四部门补层级，其余五部门不推测。
- 上级负责人/CTO以有效业务职责识别，不以权限角色识别；真实人选仍由 HR 维护。
- 模板的 PM、产品经理、CTO 原规则和权重保持；“部门负责人”在负责人岗位解释为上级负责人。
- 部门负责人标准岗位采用现有目录值“部门负责人”；兼容同部门明确前缀写法，不自动改用户岗位文本或员工直属关系。
- 既有流程启用开关保持，未启用时报清晰提示，不擅自开启。
