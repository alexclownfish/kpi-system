# Feature Specification: PostgreSQL 生产迁移与冷部署

**Feature Branch**: `main`
**Created**: 2026-10-23
**Status**: In progress — scope changed to identity-only; real production data and cutover pending
**Input**: 在全新线上目录重新部署 PostgreSQL；仅迁移旧 SQLite 的身份、组织和 RBAC 数据，不迁移旧考核数据。

## 用户修订范围（2026-10-23）

新库仅复制九张表的记录：`departments`、`job_positions`、`employees`、`roles`、`permissions`、`user_roles`、`role_permissions`、`data_scopes`、`role_data_scopes`。当前应用的其他表**只创建结构，不复制旧记录**；旧考核、模板、评分、签字元数据及审计在新库中为空。旧 SQLite 全库及签字文件仍须完整备份、核验、保留作回退。现有全量迁移模式仍可用，但不是本次上线所选路径。此范围是用户明确要求的宪章 V 例外，风险与替代方案见 plan.md。

## User Scenarios & Testing

### User Story 1 - 保留账号权限，清空旧考核 (Priority: P1)

运维人员从旧服务取得一致性数据库副本与签字附件归档，只迁移员工、组织和权限。原账号可登录并保持授权；旧考核及模板不出现在新库。校验失败时，旧服务仍可恢复使用。

**Why this priority**: 用户明确选择保留身份与权限，但不保留新库中的旧考核数据。

**Independent Test**: 以旧库副本演练，核对九表行数、主键、关联、序列及至少一个有效超级管理员；非九表行数为零。

**Acceptance Scenarios**:

1. **Given** 旧服务已有员工及角色，**When** 对一致性副本执行仅身份迁移，**Then** 九表的行数、ID、密码哈希和关系与源库一致。
2. **Given** 旧库含考核、模板与签字，**When** 仅身份迁移成功且普通应用尚未启动，**Then** 新库对应表结构存在、非九表均为零；应用启动后仍不显示旧历史考核，新产生的设置/审计不算旧记录。
3. **Given** 迁移失败或需回退，**When** 运维人员停止切换，**Then** 旧 SQLite 全库与签字附件可恢复，未被删除或修改。
4. **Given** 旧库至少有一个有效超级管理员，**When** 新库启动，**Then** 该管理员以原密码登录，普通员工不能越权。

---

### User Story 2 - 从空目录重新部署 (Priority: P1)

运维人员在新服务器空目录拉取代码、配置私密参数、启动数据库和应用，并通过原有域名使用系统。重建应用后数据仍在。

**Why this priority**: 服务器目录无源码，部署必须从仓库获取可复现版本。

**Independent Test**: 在隔离目录克隆发布提交、部署、检查健康状态，重建并再次核对账号与权限。

**Acceptance Scenarios**:

1. **Given** 目标目录为空，**When** 执行首次部署步骤，**Then** 完整代码被拉取且服务健康。
2. **Given** 数据库暂时不可用或凭据错误，**When** 后端启动，**Then** 明确失败，不静默连接本地 SQLite。
3. **Given** 应用已运行，**When** 重建容器，**Then** 九表数据仍在，旧考核仍未混入。

---

### User Story 3 - 权限与备份验收 (Priority: P2)

管理员在新系统里检查部门、岗位、角色、权限及数据范围。运维人员执行新库备份/恢复演练，并保留可恢复的旧库和签字归档。若需开展新考核，另行建立模板并验收完整流程。

**Why this priority**: 健康检查不能证明身份和授权正确，更不能证明旧档案可恢复。

**Independent Test**: 原账号登录、允许/拒绝权限测试、九表核对、旧档案与新库隔离恢复。

**Acceptance Scenarios**:

1. **Given** 九表迁移通过，**When** 检查部门/岗位/角色及数据范围，**Then** 层级与授权和源库一致。
2. **Given** 新库已上线，**When** 备份并在隔离库恢复，**Then** 九表及空白历史业务状态与备份一致。
3. **Given** 需要旧考核与签字，**When** 查阅新库，**Then** 明确提示旧记录只在旧库/归档中，不误称已迁入。

### Edge Cases

- 空目录并不代表旧 Docker 命名卷不存在；发现同名卷时停止并核对。
- 所有应用表结构应存在，但只有约定九表复制旧数据；模板、考核、评分、确认、审计及签字元数据没有旧记录。
- 旧库的非迁移表可含外键孤儿；只要九表内部关系完整，不应让被排除表的遗留问题阻断仅身份迁移。
- 旧数据库可能正有写入，副本必须一致，切换时必须冻结写入。
- `SEED_HONGXING_CATALOG=false` 时旧模板不会自动出现，可能无法立刻创建考核；模板来源须单独安排。
- 数据库密码、JWT 密钥和临时密码不得入库或打印到日志；已在聊天公开的 JWT 密钥必须轮换，现有会话会失效。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 显式支持 PostgreSQL 连接，失败不得回退到 SQLite。
- **FR-002**: 系统 MUST 保留 SQLite 模式供现有环境和测试使用。
- **FR-003**: 本次迁移 MUST 只复制约定九表记录，保留主键、字段、账号密码哈希、角色授权及数据范围；其他源业务表记录 MUST 不进入新库。
- **FR-004**: 目标库 MUST 先创建应用需要的全部表结构；迁移报告 MUST 核对九表行数、主键、关联、序列及有效超级管理员；在普通应用首次启动前非九表须为零记录。启动后新生设置和审计可以出现，但旧历史不得被导入。
- **FR-005**: 首次部署 MUST 从空目录获取源码并建立不公开数据库端口的持久化服务。
- **FR-006**: 部署 MUST 安全配置密钥、等待数据库就绪、明确健康检查及错误；迁移验收标记只可在核对通过后创建。
- **FR-007**: 历史账号登录、部门岗位层级、角色权限及数据范围 MUST 在新库正常工作；不得误称旧考核/模板/签字已迁入。
- **FR-008**: PostgreSQL MUST 有全量数据库备份及隔离恢复；旧 SQLite 全库和签字附件 MUST 完整封存并验证可恢复。
- **FR-009**: 切换失败时 MUST 能回到保留的旧服务、旧数据库和附件。
- **FR-010**: 已公开的生产 JWT 密钥 MUST 在上线前轮换，并说明原登录会话会失效。

### Key Entities

- **迁移九表**: 部门、岗位、员工、角色、权限、用户角色、角色权限、数据范围、角色数据范围。
- **目标空白业务结构**: 模板、考核、评分、确认、审计等表结构存在，旧记录不复制。
- **旧档案**: 原 SQLite 全库及签字材料，仅用于留存、核查和回退，不导入本次新库。
- **部署凭据**: 数据库密码、JWT 密钥及首次管理员密码，仅保存在运行环境。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 九表行数和主键与源快照 100% 一致，九表内部关联检查 0 错误。
- **SC-002**: 至少一个原有有效超级管理员用原密码登录，允许/拒绝权限场景各通过一次。
- **SC-003**: 普通应用首次启动前目标全部应用表结构存在，非九表行数为 0；启动后页面无旧考核、模板与签字历史，新产生的设置/审计记录来源可解释。
- **SC-004**: 容器重建后九表数据保留；旧 SQLite 与签字附件归档在隔离环境恢复并核对摘要。
- **SC-005**: 新库备份在隔离环境恢复，九表数量与空白历史业务状态一致。

## Assumptions

- 目标路径 `/mnt/datadisk0/project/kpiSystem` 当前已有健康 PostgreSQL 容器；不能据此推断目标 schema 和所有表均为空，迁移前要实际确认。
- 旧生产数据库为 SQLite；实际 Docker 卷和附件路径在迁移前只读确认。
- 域名拟用 `https://kpi.auracor.net`，有效超级管理员以源库实际账号为准；现有密码哈希应迁移而非重置。
- 服务器已有 Docker Compose，且有该仓库的 SSH 读取权限。
